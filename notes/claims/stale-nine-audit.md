# The nine stale maps: the audit (Nov. 26, 2026)

The patch is `inbox/2026-11-26-stale-nine.yaml`; the reader's note is `notes/claims/stale-nine.md`. I read every source the patch maps, at its page, in the copy on the owner's Drive. I read scans as page images, and books with a text layer as text, with the page number checked on the page. I changed nothing on Drive, and every copy is deleted.

## What I checked in the patch as a whole

Each `edit` changes no word of any line. Each sets only the map (and, on one entry, its variants, below). Each carries the rev that `./bib show` prints today, and each map's line hash is the hash of the line as it stands. I applied the patch in memory (`merge.apply_patch(dry=True)`): all nine maps come out fresh, and no line changes. The one change to a note is the cite I added on `cal.1966-05-04.china-leadership`. `./bib patch-check` shows 0 errors. Its 8 warnings say that an `edit` sets only the map; that is needed here, because an additive op cannot run on a stale map.

One rule I applied throughout, as the reader did: a map names whole parts of the line, a sentence or a clause, and nothing smaller. Where a source bears out the main claim of a part but not every detail in it, the part is mapped to it, and the note's parenthetical says what the source has. Where a source has only a side detail of a part, the part is not mapped to it.

A `via` row stands for the record a work's note cites, and for the parts of the line that the work's passage draws from that record (R35, R37). It does not stand for the words of the note itself (R35a). The reader kept several old `via` rows at `all`, or at letters, without reading the passage each note belongs to. I read those passages and narrowed those rows.
