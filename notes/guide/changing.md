# Changing things

Moved word for word from CLAUDE.md, Nov. 10, 2026 (the owner: "I approve both"); CLAUDE.md keeps the core and an index of these guides.

**Directly** (you are working in this repo): edit the section file, then

```
./bib new-id cal 1961-10-27 berlin-and-vienna   # an unused id
./bib check            # must end "0 errors"; deal with new warnings
./bib build            # build/<key>.html and build/series.html (a page alone: ./bib build congress | names | works | cal ...)
./bib links            # links between the built pages whose anchors are missing
```

Every YAML file is parsed once a run, and the parse kept in `.cache/yaml` (git-ignored) by path, modification time and size, so a later run parses only what changed: `check` takes about 8 s, a full build about 35 s, a page 15-20 s. A link to another page's anchor that a later build lost lands on the page's top; `./bib links` lists them.

**By patch**: when another session or a person will merge your work, or you cannot touch the repo. Write `inbox/<date>-<name>.yaml` and run `./bib merge inbox/<file> [--dry-run] [--archive]`:

```yaml
patch: berlin-autumn                  # name, shown in conflict records
by: who wrote it
ops:
  - add:                              # placed by date (calendar), by subject
      entry: {id: ..., when: ..., date: ..., thread: ..., c: ..., n: ...}
      section: II.D                   #   ("Alphabetical"), or by year; or say
      after: kja.wyden-bay-of-pigs    #   section/after
  - edit:
      id: cal.1961-08-13.berlin-and-vienna
      base: 7047fc46                  # the rev ./bib show printed when you read it
      set: {n: 'New note …'}
      unset: [r]
  - tag:     {id: ..., add: [topic:berlin], remove: [todo]}
  - move:    {id: ..., section: II.E, after: ...}
  - delete:  {id: ..., base: ...}
  - combine: {keep: ID, drop: ID}
```

Always give `edit` and `delete` a `base`. With it, the merge is three-way: fields only you changed apply, fields only others changed stay, and a field both changed becomes a conflict. Without it, your values simply overwrite.

Additive ops (the owner's request, Oct. 30, 2026: "a performant, compute-economizing solution" for parallel readers; `notes/extensions/memos/volume.md`, §6; `tools/bib/addops.py`, its STYLE): what only adds to an entry needs no `base` and merges in either order: `cite: {id, item: '[[w.card]], 123', on: 'Moscow will send Zorin.'}` (the work out of "To check:" into the run of works read, its claim-map row; `on:` the words of the part of the line it supports, or a field, `on: time`; none, the whole line as it stands), `add-words: {id, after, words, item}` (new words into the line as a part of their own, with their source), `primary: {id, text, on}`, `to-check: {id, add}`, `check: {id, text}`, `src: {id, row, on}` (or `rows`), `names: {id, add, tags}`, `also: {id, add}`, `variant: {id, on or field and value, witness, reads, at}`, `follows: {id, add}` (with `basis: <a page, or "the printed order alone ([[w.card]], 123)">` where the two lines do not show the order: the op writes "The order: after [[id]], <basis>." into the note, addops.py, STYLE 11; and `follows: {id, remove: [<id>], why: <the record or the words>}`, by which an audit takes out a link the entry has that it found wrong, and with it the note's sentence "The order: after [[id]], ...": the reader's brief, R25c; a link held for a second reader is kept as an op in `inbox/held/`, which no merge reads). An op written before Nov. 25, 2026 that names units by letter (`units: 'A, C'`) carries `base:` and is refused where the line has changed since. An `edit` that changes words already in a calendar line states `kind: reword` or `kind: correct` (R22; `tools/bib/cuts.py`, STYLE 11), and keeps the line's cut marks, each after its words. An `edit` may not drop a work read or a "Check:" from a note; where it answers or rewords a Check it lists that sentence, or its opening words, in `settles: ['Check: the day of the call.']`, and the audit reads the list. Within a patch the adds go first. A new entry is claimed first in the ledger, `inbox/new-entries.tsv` (`./bib ledger add DATE THREAD ID "words" PATCH`; `./bib ledger find DATE [--until DATE] [--thread T]` the day's entries, tree and ledger; `./bib ledger drop PATCH ID...` releases a patch's claim on an id it no longer adds, under the file's lock (Nov. 18, 2026: readers and audits marking or removing lines by hand while others claimed lost their lines; never edit the ledger by hand); `tools/bib/ledger.py`), and an additive op on a claimed id not yet in the tree waits in `inbox/deferred.yaml` until it lands. `./bib patch-check PATCH [--legacy]` holds a patch to the rules before it is handed in (`tools/bib/patchcheck.py`): the patch applied in memory, the entries it adds, edits or adds to held to `check`'s own rules for an entry, by `check`'s functions (`entry_problems`: `when` against `date`, `when_matches_date`; `thread`, `also` and `to` a thread's slug, not an alias; every `[[id]]` an entry; the date in the section it lands in, January 1966's two among them), the witnesses' (`witnesses.problems`: a `via x.` row's witness reached from an item of the note) and the claim maps' (`claims.problems`: a `src` row naming what the note prints), an error the tree already had not the patch's, each message saying the fix (patchcheck STYLE 8), so a patch it passes passes `check` once merged; and each calendar `add` held to R25a, the fields (the owner, Nov. 19, 2026: "Could we fix that? Permanently?"; `tools/bib/fields.py`, patchcheck STYLE 10): a clock time or a part of the day in `c`, `when` or a parenthetical of `n` without `time` or `time_range` is an error [fields-time] (not another day's or another time's hour, "the morning of the 17th", "the next afternoon"; not a "Check:" or "To check:", nor the gloss on another entry's link; not "at NN" that is an age, a rate or a page), an hour that recurs ("daily", "in shifts") a warning [fields-time-habitual], a loose date's position merge cannot set itself ("July, about the 20th", "early July" in `c`, "the eve of"; "July, late" merge places) without `at` an error [fields-at], a gazetteer place named in `c` without `place` a warning [fields-place] (a fifth of its hits a subject, not the scene; patch-check prints the first three and the count), each silenced by setting the field or by the tag `ok:fields-time`, `ok:fields-at`, `ok:fields-place`; `./bib fields ID...` or `./bib fields --patch P` prints the findings alone; `./bib merge --auto PATCH...` is the rolling merge: patch-check (`--legacy` for a patch written before the ledger), apply, the deferred ops, the conflicts on `n` that `notemerge` joins with no problem and those on `src` over the same `c` joined (both sides kept), the ledger pruned, the patch archived; it stops at a patch with errors and prints the conflicts left and a sample, one changed entry in ten, to read. `./bib plan-readers CARD...` groups works by the entries they already share, a group a reader (`tools/bib/planreaders.py`).

**Changing the code** (`tools/`; the owner, Nov. 19, 2026: tests first, then rewrites behind them): the tests are in `tests/` (`tests/README.md`). Run the fast suite before a push (`python -m pytest -q -m "not slow"`, about a minute; CI runs it before `check`, and a failure stops the deploy). A golden test that fails names what changed: a regression to fix, or a meant change whose goldens are rewritten (`pytest --update-goldens`), read and committed with it. A rewrite is proved byte-identical on the full data with `python3 tests/ab.py main HEAD` (both versions of the code, the same data, every built file compared). The tools read the data from `BIB_ROOT` when it is set (`BIB_ROOT=tests/fixture ./bib check`), else this checkout.

**Git**: run `./bib setup` once per clone. Section files then merge entry by entry (`.gitattributes`): both sides' new entries are kept in order, and a field changed on both sides becomes a conflict record instead of `<<<<<<<` markers.

**Before a PR and merge to `main`** (the owner, Nov. 18, 2026): `./bib check` (0 errors), `./bib readme --check` in a clean copy of the tree (`git worktree add`: uncommitted entries and cards would count) (README.md's calendar pages and counts; if stale, `./bib readme` there and commit it: tools/bib/readme.py), then the build, then `./bib pages` (every page's size against its budget, `pages.yaml`; exit 1 while a page not exempt is over it and a split could bring it in; one person's Names entry over it is reported). A page over budget: `./bib pages --plan` writes the split its structure proposes (Names by surname range, Works by letter, the Executive and Congress by their parts, a calendar part by quarter, then month: `lists/cal/list.yaml`), the next build applies it (the parts, their bars, the links from every page, and the old address forwarding by anchor: tools/bib/pages.py), then `./bib links` (0 missing anchors, 0 missing pages) and `./bib readme` (the other pages' table). The calendar's index (`cal.html`), with its threads, is rebuilt by every build, the deploy's included (`.github/workflows/pages.yml`), so a change in the threads reaches it with no step of its own.
